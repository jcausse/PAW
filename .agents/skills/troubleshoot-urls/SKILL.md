# Troubleshoot URLs Skill

## Purpose

Verify that all internal URLs and routes in JSP pages and custom tags comply with JSTL context path resolution (`<c:url>`) and are not hardcoded.

## Background

Under servlet containers (e.g., Jetty, Tomcat) or reverse proxies, the application may be hosted under a non-root context path (e.g., `/swappr` or `/paw-2026b-08`). 
- Hardcoded URLs like `href="/account"` or `action="/login"` bypass context-path resolution and break into 404 Not Found errors when deployed.
- Every internal URL attribute in HTML or custom tags must be resolved using `<c:url value="..." var="..."/>` and held in a variable, or printed with an inline `<c:url value="..."/>`.
- Double `<c:url>` resolution must be avoided: tags that internally wrap parameters with `<c:url>` (e.g. `<paw:user>` on `href` or `<paw:pagination>` on `baseUrl`) expect raw path literals and should not receive pre-resolved variables.

## When to Use

- **Mandatory check**: After creating, modifying, or refactoring any `.jsp` file or `.tag` file.
- When troubleshooting 404 errors, broken buttons/links, or URL routing issues.
- As part of pre-commit or pre-PR verification alongside `mvn clean compile`.

## Workflow

### 1. Run the Troubleshooter via Makefile

Run the unified compliance scanner from the repository root:

```bash
make troubleshoot
```

### 2. Inspect the Output

The script scans all files in `webapp/src/main/webapp/WEB-INF/` and reports:
- **Clean output**:
  ```
  === Swappr JSP / Tag URL & c:out Troubleshooter ===
  Scanning 48 files in webapp/src/main/webapp/WEB-INF...

  --- Summary ---
  Files scanned: 48
  ✓ No missing URL variables or unmanaged paths found! All URLs follow JSTL conventions.
  ```
  Note that the amount of files can differ from the example, as development continues.

- **Flagged output**:
  Provides file path, line number, problematic snippet, and the exact suggested fix. Always check the suggested fix
  makes sense for the actual problem, as it is generated by a script with pre-defined text, not an actual AI agent.

### 3. Run Targeted Sub-Checks (Optional)

You can run individual sub-scripts by passing `ARGS`:

```bash
# Scan for hardcoded / non-variable URL attributes (href, action, src)
make troubleshoot ARGS=find_urls

# Check for inline <c:url> tags that don't store in a variable
make troubleshoot ARGS=check_curl_no_var

# Check for relative path attributes missing leading '/'
make troubleshoot ARGS=check_relative_paths

# Check embedded paths in <script> blocks
make troubleshoot ARGS=check_scripts

# Run all individual sub-scripts sequentially
make troubleshoot ARGS=--all
```

### 4. How to Fix Flagged Issues

- **Hardcoded attribute in a JSP / tag** (e.g. `<paw:linkButton href="/account" .../>`):
  ```jsp
  <%-- Add <c:url> to define a variable --%>
  <c:url value="/account" var="accountUrl"/>
  <paw:linkButton href="${accountUrl}" .../>
  ```
- **Raw path in `<c:set>`**:
  Replace `<c:set var="myUrl" value="/my/path"/>` with `<c:url value="/my/path" var="myUrl"/>`.

### 5. Exceptions (Internally Handled Tags)

Do **NOT** wrap attributes in `<c:url>` before passing them to tags that resolve them internally:
- `<paw:pagination baseUrl="/account/listings" .../>` — `pagination.tag` calls `<c:url>` internally on `baseUrl`.
- `<paw:user href="/account" .../>` — `user.tag` calls `<c:url>` internally on `href`.

### 6. How to check for nested context path resolution

If the flagged snippet / use case is inside a `<paw:` tag, like (e.g. `<paw:pagination>`), it is possible that the
component the URL is being passed to internally handles it using `<c:url>`. If applicable, check the custom component 
for possible nested `<c:url>`s before proceeding with any fix.
